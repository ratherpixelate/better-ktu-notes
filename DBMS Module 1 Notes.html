Databases and DBMS

DefineAdded

DatabaseA collection of related data. Data is known facts that can be recorded and have an implicit meaning. Information is data with explicit meaning, that is, processed data.

DBMSDatabase management system: software that lets users create and maintain a computerised database. The database system is the DBMS software together with the data itself (and sometimes the applications).

What a DBMS does

  • Define the database: data types, structures and constraints.
  • Construct it: load the initial data onto secondary storage.
  • Manipulate it: retrieval (queries, reports) and modification (insert, delete, update), also through web applications.
  • Process and share it among concurrent users while keeping the data valid and consistent.
  • Other features: security against unauthorised access, "active" processing (triggers), presentation of data, and maintenance of the database and programs over its lifetime.

Types of database applications

Traditional: numeric and textual databases. More recent: multimedia, geographic information systems (GIS), data warehouses, real-time and active databases. This course focuses on the traditional kind.

Scope and objectives of a database project

AddedYour slides use the UNIVERSITY and COMPANY examples but never say how to scope a project. The syllabus asks for it, so here is the short version.

  • Mini-world: the part of the real world the database models, for example one college's activity points.
  • Objectives: the questions the database must answer and the transactions it must support (for example "list students below the required points").
  • Scope: what is in (entities, users, reports) and what is deliberately left out. A small, well-defined scope is easier to design and test.
  • Users: who inserts, who queries, who administers.

Importance of a DBMS in real-world applications

  • Banking and reservations: hundreds of concurrent transactions per second (OLTP) with correct, current data.
  • Universities and hospitals: many departments share one consistent record of students or patients.
  • E-commerce and the web: pages generated from a database, with XML or PHP/JavaScript on top.
  • Data warehouses and data mining: large historical data analysed for decisions.

Roughly in the order of history: hierarchical and network models (1960s to 70s), relational (Codd 1970, products from the early 80s), object-oriented (late 80s, little uptake), then object-relational and web/XML data.

Database approach: characteristics and advantages

ListExplain

Main characteristics (file system vs database)

CharacteristicMeaning
Self-describingThe catalog stores a description of the database (structures, types, constraints). This description is meta-data, and it lets the same DBMS software work with any database.
Program-data independenceData structures and storage can change without changing the programs that access the data. In file processing the structure is inside the program.
Data abstractionA data model hides storage details and shows a conceptual view. Programs use model constructs, not storage details.
Multiple viewsEach user group sees only the data it needs.
Sharing and multi-user transactionsConcurrency control makes each transaction execute correctly or abort. The recovery subsystem makes sure a completed transaction's effect is permanent.

Advantages of using a DBMS

  • Controlling redundancy in storage and in development effort.
  • Sharing of data among users, and multiple interfaces for different classes of users.
  • Restricting unauthorised access.
  • Persistent storage for program objects, and indexes for efficient query processing.
  • Backup and recovery services.
  • Representing complex relationships among data and enforcing integrity constraints.
  • Inferences and actions from stored data using deductive and active rules.
  • Further implications: enforcing standards, shorter development time for each new application, flexibility to change structures, up-to-date information, economies of scale.

When not to use a DBMS

  • Costs: high initial investment (possibly extra hardware), and overhead for generality, security, concurrency control, recovery and integrity.
  • Unnecessary when: the database and applications are simple, well defined and not expected to change; there are stringent real-time requirements the overhead would break; multiple users do not need access.
  • Insufficient when: the data is too complex for the model, or users need special operations the DBMS does not support.

The initial state is the state when data is first loaded. A valid state satisfies the structure and all constraints. A schema diagram is a picture of the schema, and a schema construct is one component of it, such as STUDENT.

Three-schema architecture

Proposed to support program-data independence and multiple views. Commercial DBMSs do not follow it exactly, but it explains how a DBMS is organised.

LevelDescribesUses
Internal schemaPhysical storage structures and access paths such as indexesA physical data model

Data independence

TypeAbility to changeWithout changing
LogicalThe conceptual schemaExternal schemas and application programs
PhysicalThe internal schema (new indexes, reorganised files)The conceptual schema

When a lower schema changes, only the mappings between levels change. The higher schemas stay the same, so application programs need no change. Logical independence is the harder one to achieve.

Interfaces

  • Stand-alone query interface (for example SQL*Plus).
  • Programmer interfaces: embedded SQL (SQLJ), procedure-call (JDBC, ODBC), or a database programming language (PL/SQL).
  • User-friendly: menu-based, forms-based (naive users), graphical, natural language, speech, web browser, parametric (bank-teller function keys).
  • DBA interfaces: create accounts, grant authorisations, set system parameters, change schemas or access paths.

Utilities

Loading data from files (with conversion), backup, file reorganisation, report generation, performance monitoring, and sorting, user monitoring and compression. CASE and application-development tools are separate.

Architectures

ArchitectureIdea
CentralisedDBMS, hardware, applications and user-interface processing all on one system. Remote terminals only display, all processing is at the central site.

ER model: entities, attributes and keys

DefineDraw

EntityA specific object or thing in the mini-world, for example the EMPLOYEE John Smith or the Research DEPARTMENT. An attribute is a property that describes it. A specific entity has a value for each attribute.

Each attribute has a value set (domain or data type): integer, string, enumerated and so on.

Types of attributes

TypeMeaningExample
Simple (atomic)One indivisible valueAge, Sex
CompositeMade of components, possibly in a hierarchyName(FirstName, MiddleName, LastName); Address(Street, City, State, Zip)
MultivaluedSeveral values for one entity. Written in braces.{Color} of a CAR, {PreviousDegrees}
DerivedComputed from another attribute or from stored dataAge from Birth_date; Number_of_employees of a department

Composite and multivalued can nest: {PreviousDegrees(College, Year, Degree, Field)} is a composite multivalued attribute with four components.

Entity type, entity set and keys

  • Entity type: entities with the same basic attributes (the schema), such as EMPLOYEE. Entity set: the entities of that type currently in the database (the state). The same name often serves for both.
  • Key attribute: every entity must have a unique value for it, for example SSN of EMPLOYEE. A key can be composite, and an entity type can have more than one key.
  • Example: CAR has two keys, Vehicle_id (VIN) and Registration, where Registration is composite (Number, State).
  • In the diagram a key is underlined.

Relationships, constraints and weak entities

DefineDrawDifferentiate

RelationshipRelates two or more distinct entities with a specific meaning, for example EMPLOYEE Franklin Wong manages the Research DEPARTMENT. Relationships of the same kind form a relationship type. Its degree is the number of participating entity types (binary = 2, ternary = 3).

  • Relationship type is the schema: name, participating entity types, constraints. The relationship set is the current set of relationship instances (the state).
  • More than one relationship type can exist between the same entity types. MANAGES and WORKS_FOR both join EMPLOYEE and DEPARTMENT, with different meanings.
  • A relationship type can have attributes, such as Hours on WORKS_ON. Hours depends on the (employee, project) pair. On a 1:N relationship such an attribute can move to the N-side entity.

Recursive relationship

The same entity type takes part twice in distinct roles. SUPERVISION relates an EMPLOYEE in the supervisor role to another EMPLOYEE in the supervisee role. Role names must be shown in the diagram.

Structural constraints

ConstraintSpecifiesValuesNotation
Cardinality ratioMaximum participation1:1, 1:N (or N:1), M:NNumbers on the edges
Participation (existence dependency)Minimum participationTotal (mandatory, at least one) or partial (optional, zero allowed)Double line for total, single line for partial

(min,max) notationOn each participation of entity type E in relationship R: every entity of E takes part in at least min and at most max relationship instances. Default is (0,n). Read the pair next to the entity type, looking away from it.

Weak entity type

Weak entityAn entity type with no key attribute of its own. It must take part in an identifying relationship with an owner (identifying) entity type. Its entities are identified by the partial key together with the owner entity they are related to.

  • Example: DEPENDENT is weak. Dependent_name is the partial key, EMPLOYEE is the owner, and DEPENDENTS_OF is the identifying relationship.
  • A weak entity always has total participation in the identifying relationship, because it cannot exist without its owner.
  • Diagram: double rectangle, double diamond, partial key dotted-underlined.

Relational model and its constraints

DefineDifferentiateNumerical

Proposed by E. F. Codd (IBM) in 1970. A relation is a mathematical concept based on sets, and informally it looks like a table of values.

InformalFormal
TableRelation
Column headerAttribute
All possible column valuesDomain
RowTuple
Table definitionSchema of a relation
Populated tableState of the relation

Formal definitions

  • Schema R(A1, …, An): relation name plus attributes, for example CUSTOMER(Cust-id, Cust-name, Address, Phone#). Its degree is n.
  • Domain: the set of valid values for an attribute, with a logical definition and a data type or format. The attribute name gives the role the domain plays: the domain Date can be used for both Invoice-date and Payment-date.
  • Tuple: an ordered list of values, one from each attribute's domain (or null). A row of CUSTOMER is a 4-tuple.
  • Relation state r(R) is a subset of the Cartesian product of the domains: r(R) ⊆ dom(A1) × … × dom(An).

WorkedLet dom(A1) = {0,1} and dom(A2) = {a,b,c}. The product has 2 × 3 = 6 tuples: <0,a>, <0,b>, <0,c>, <1,a>, <1,b>, <1,c>. One possible state is {<0,a>, <0,b>, <1,c>}, which has three 2-tuples.

Characteristics of relations

  • Tuples are not ordered, because a relation is a set. Attribute order in the schema is taken as fixed.
  • Every value is atomic (indivisible) and from the attribute's domain.
  • null stands for unknown or inapplicable.
  • Notation: t[Ai] or t.Ai is the value of attribute Ai in tuple t.

Integrity constraints

Constraints are conditions that must hold on every valid state.

ConstraintRule
DomainEvery value must come from the domain of its attribute (or be null, if allowed).
KeyNo two tuples have the same value for the key. See keys below.
Entity integrityNo primary-key attribute of any tuple may be null, because the primary key identifies the tuple. Other attributes may also be NOT NULL.
Referential integrityInvolves two relations. A foreign key value in the referencing relation must be either the value of an existing primary key in the referenced relation, or null. If it is null it must not be part of the FK relation's own primary key.
SemanticApplication rules the model cannot express by itself, such as "an employee works at most 56 hours a week". Use triggers or assertions.

Keys

  • Superkey: a set of attributes SK such that no two tuples in any valid state have the same SK value.
  • Key: a minimal superkey. Removing any attribute stops it being a superkey. Every key is a superkey but not the other way round, and any attribute set that includes a key is a superkey.
  • Candidate keys: all the keys of a relation. One is chosen as the primary key, underlined, and the others are unique (secondary) keys. Rule of thumb: pick the smallest.
  • Foreign key: attributes FK in R1 that refer to the primary key PK of R2. A tuple t1 in R1 references t2 in R2 if t1[FK] = t2[PK]. Shown as an arrow from R1.FK to R2.
  • An artificial (surrogate) key, such as a sequence number, can be added when no natural key exists.

WorkedCAR(State, Reg#, SerialNo, Make, Model, Year). Keys: {State, Reg#} and {SerialNo}. {SerialNo, Make} is a superkey but not a key, because Make can be removed.

Counting superkeys. R(A, B, C) with A as the only key: a superkey is any subset that contains A, so 22 = 4 superkeys (A, AB, AC, ABC).

CheckYour slide on CAR says "we chose SerialNo as the primary key" but the next slide's table picks LicenseNumber. Both are candidate keys, so either is allowed. In an exam, state which one you choose and underline only that one.

  • Each column in the mapping became a column here. The composite key of WORKS_ON and DEPENDENT is a table-level PRIMARY KEY (a, b).
  • ON DELETE CASCADE is used where the child cannot exist without its parent: locations, works-on rows and dependents. EMPLOYEE.Dno has no rule, so deleting a department that still has employees is rejected (RESTRICT is the default).
  • SUPERVISION uses SET NULL: if a supervisor is deleted, the subordinates stay with no supervisor.

The circular reference

DEPARTMENT refers to EMPLOYEE (manager) and EMPLOYEE refers to DEPARTMENT (Dno). Neither table can be created first with both foreign keys. The usual fix: create DEPARTMENT without the manager foreign key, create EMPLOYEE, then add it:

ALTER TABLE DEPARTMENT
  ADD CONSTRAINT fk_mgr FOREIGN KEY (Mgr_ssn) REFERENCES EMPLOYEE(Ssn);

Rows have the same chicken-and-egg problem: insert the department with Mgr_ssn = NULL, insert the employee, then update the department's manager. This is why Mgr_ssn must be allowed to be null.

Run resultIn my test I left the manager foreign key out (SQLite cannot add one with ALTER). The result shows why it matters: a department row with Mgr_ssn = '333445555' was accepted though no such employee existed, and deleting an employee who was a manager was also accepted, leaving a dangling reference. With the ALTER above, both are rejected.

Tables, relationships and foreign keys in action

AddedWrite SQLTrace

Relationships between tables exist only through matching key values, so you use them in queries with a join:

SELECT E.Fname, P.Pname, W.Hours
FROM EMPLOYEE E
  JOIN WORKS_ON W ON E.Ssn = W.Essn
  JOIN PROJECT  P ON W.Pno = P.Pnumber;

With two sample employees on ProductX this returns (Franklin, ProductX, 10) and (John, ProductX, 32.5). Each ON clause is one foreign key matched to the primary key it references.

One-page cheat sheet

DBMS basics

  • Define, construct, manipulate, share
  • Self-describing catalog (meta-data)
  • Program-data independence, views, abstraction
  • Concurrency control and recovery
  • Don't use for simple, real-time, single-user cases

Users

  • On the scene: DBA, designer, end users
  • End users: casual, naive, sophisticated, stand-alone
  • Behind the scene: DBMS designers, tool developers, operators

Three schemas

  • External = views
  • Conceptual = whole database
  • Internal = storage
  • Logical independence: change conceptual, keep external
  • Physical independence: change internal, keep conceptual

Design phases

  • Requirements → conceptual (ER) → logical (relational) → physical

ER symbols

  • Rectangle entity, double = weak
  • Diamond relationship, double = identifying
  • Oval attribute: underline key, double multivalued, dashed derived
  • Double line total participation

Constraints

  • Ratio = max: 1:1, 1:N, M:N
  • Participation = min: total or partial
  • (min,max) on each side, read away from the entity

Relational constraints

  • Domain, key, entity, referential, semantic
  • Insert: any can break
  • Delete: only referential. RESTRICT, CASCADE, SET NULL
  • Update PK = delete + insert

Keys

  • Superkey: unique
  • Key: minimal superkey
  • Candidate → primary
  • FK refers to a PK, or is null

Mapping steps

  • 1 strong entity → relation
  • 2 weak entity → owner PK + partial key
  • 3 1:1 → FK (total side), merge or cross-reference
  • 4 1:N → FK on N-side
  • 5 M:N → new relation, PK = both FKs
  • 6 multivalued → new relation
  • 7 n-ary → new relation with n FKs

Explain the characteristics of the database approach and its advantages over file processing. (7)

Self-describing catalog, program-data independence, abstraction, multiple views, sharing with transaction support. Then advantages: less redundancy, access control, backup and recovery, integrity constraints. Add when not to use one. See Database approach.

Describe the three-schema architecture. How does it give data independence? (7)

Draw the three levels and two mappings. Define logical and physical independence. State that only the mappings change when a lower schema changes. See Models, schemas, architecture.

Differentiate database schema and database state. (3)

Schema is the description (intension), changes rarely. State is the actual data at a moment (extension, instance, snapshot), changes with every update. A valid state satisfies the schema and constraints.

Who are the database users? Explain the end-user categories. (5)

Actors on the scene versus workers behind the scene, then casual, naive, sophisticated, stand-alone with an example each. See Database users.

Explain the phases of database design. (3 or 5)

Requirements analysis, conceptual design (ER), logical design (mapping), physical design, with the output of each. Mention the parallel functional analysis for application design. See Design process.

Define entity, attribute and relationship. Explain the types of attributes with examples. (7)

Simple, composite, multivalued, derived. Include the nested example {PreviousDegrees(College, Year, Degree, Field)}. Add key attributes and the symbols. See Entities and attributes.

Explain cardinality ratio and participation constraints, including the (min,max) notation. (7)

Ratio gives the maximum, participation the minimum. Give the MANAGES and WORKS_FOR (min,max) pairs. See Relationships and constraints.

What is a weak entity type? Give an example. (3)

No key of its own, identified through an owner entity and a partial key, with an identifying relationship and total participation. DEPENDENT of EMPLOYEE.

Draw the ER diagram for a given scenario (library, hospital, college) and state the constraints. (10)

Use the five-step method: entities, attributes with keys, relationships, ratios and participation, weak entities. Label every relationship with its ratio. See Building an ERD.

Explain the relational constraints. How are they violated by insert, delete and update? (7)

Domain, key, entity integrity, referential integrity. Then the table of violations and the three delete remedies. See Relational model.

Differentiate superkey, candidate key, primary key and foreign key. (5)

Superkey is unique, key is minimal, candidate keys are all keys, primary key is the chosen one, foreign key refers to another relation's PK. Use the CAR example.

Explain the ER-to-relational mapping algorithm and map a given ER diagram to a relational schema. (10)

Go through steps 1 to 7 in order and apply each to the diagram. Mark PKs and FKs. See ER to relational mapping.

Write the SQL to create the tables for a sample schema with primary keys, foreign keys and constraints. (7)

One CREATE TABLE per relation in parent-to-child order, with NOT NULL, PRIMARY KEY, FOREIGN KEY … REFERENCES and ON DELETE rules. Handle any circular reference with ALTER TABLE. See Creating tables in SQL.
