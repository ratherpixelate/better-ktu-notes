Why normalise: design guidelines and anomalies

ExplainExample

NormalizationThe process of decomposing "bad" relations into smaller relations, using keys and functional dependencies, so that redundancy and anomalies are removed. A normal form is a condition on keys and FDs that a relation must meet.

Four informal guidelines

GuidelineMeaning
1. Clear semanticsEach tuple represents one entity or relationship instance. Do not mix attributes of different entities in one relation. Use foreign keys to refer to other entities.
2. No anomaliesDesign so there are no insertion, deletion or update anomalies. If one is unavoidable, note it so applications handle it.
3. Few nullsAvoid attributes that are often NULL. Put them in a separate relation with the key. Nulls arise when a value is not applicable, unknown, or known but unavailable.
4. No spurious tuplesRelations must satisfy the lossless join condition: a natural join of the decomposed relations must not create extra tuples.

Update anomalies

They appear when information is stored redundantly. Take EMP_PROJ(Emp#, Proj#, Ename, Pname, No_hours), where the project name repeats for every employee on the project and the employee name repeats for every project.

AnomalyWhat goes wrong in EMP_PROJ
InsertionYou cannot insert a project unless an employee is assigned to it, and cannot insert an employee who has no project yet.
DeletionDeleting a project deletes every employee tuple that works only on it. Deleting the last employee on a project also deletes the project.
ModificationRenaming project P1 from "Billing" to "Customer-Accounting" means changing every row for P1 (100 rows if 100 employees work on it). Miss one and the data is inconsistent.

Redundancy also wastes storage. The usual cause is a relation made by joining two entities, such as EMP_DEPT (employee plus department data) or EMP_PROJ.

Two properties of a good decomposition(a) Lossless (non-additive) join: extremely important, never sacrificed. (b) Dependency preservation: less strict, may be sacrificed. Both are explained in the decomposition section.

Functional dependencies

DefineNumericalAdded

Functional dependencyX → Y holds in R if, whenever two tuples have the same value for X, they must have the same value for Y. That is, for any t1, t2 in any state r(R): t1[X] = t2[X] implies t1[Y] = t2[Y]. We say X functionally determines Y.

  • An FD is a constraint on all valid states, derived from the meaning of the data. You cannot prove one from a single state, you can only disprove it.
  • If K is a key of R, then K → every attribute of R.
  • Examples: SSN → ENAME; PNUMBER → {PNAME, PLOCATION}; {SSN, PNUMBER} → HOURS.

Inference rules (Armstrong's axioms)

RuleStatement
IR1 ReflexiveIf Y ⊆ X then X → Y
IR2 AugmentationIf X → Y then XZ → YZ
IR3 TransitiveIf X → Y and Y → Z then X → Z
DecompositionIf X → YZ then X → Y and X → Z
UnionIf X → Y and X → Z then X → YZ
PseudotransitivityIf X → Y and WY → Z then WX → Z

IR1 to IR3 are sound (they only produce valid FDs) and complete (every FD that follows from F can be derived with them). The last three rules can be derived from IR1 to IR3.

Closure

  • F+, the closure of a set of FDs, is the set of all FDs that can be inferred from F.
  • X+, the closure of an attribute set X under F, is the set of all attributes that X functionally determines.

Added · methodComputing X+.

  1. Start with the result set equal to X.
  2. Look at each FD in F. If its left side is inside the result set, add its right side to the result set.
  3. Repeat step 2 until a full pass adds nothing new. That set is X+.

Example. R(A, B, C, D, E), F = {A→B, A→C, CD→E, B→D, E→A}. Find (CD)+. Start {C, D}. CD→E adds E, giving {C, D, E}. E→A adds A, giving {A, C, D, E}. A→B adds B. Result: (CD)+ = {A, B, C, D, E}, so CD is a superkey.

Is an FD implied? X → Y is implied by F exactly when Y ⊆ X+. Your slide's Example 3 asks which of CD→AC, BD→CD, BC→CD, AC→BC is not implied. (BD)+ = {B, D} (B→D adds D, then nothing more), which does not contain C, so BD → CD is not implied. The other three have closures that contain the right side. I checked this in code.

Finding candidate keys

Added · method

  1. List the attributes that never appear on the right side of any FD. They must be in every key.
  2. Attributes that appear only on right sides are in no key.
  3. Compute the closure of the must-have attributes. If it is every attribute, that set is the key.
  4. If not, add one more attribute at a time (then pairs) and test the closure. Keep only minimal sets. Every minimal set whose closure is all of R is a candidate key.

Slide Example 1. F = {A→B, B→C} on ABC: A is never on a right side and A+ = ABC, so the only key is A.

Slide Example 2. F = {A→BC, C→B, D→E, E→D} on ABCDE: A never appears on a right side, so it is in every key. A+ = ABC, and D+ = DE = E+, so A must be combined with D or E. Keys: AD and AE.

Exercise 1. R(A, B, C, D, E), F = {AB→C, C→D, D→B, D→E}. Keys: AB, AC, AD. A is never on a right side. (AB)+: AB→C, C→D, D→E gives every attribute. Since C→D→B, once A is present either C or D can replace B, so AC and AD are keys too.

Equivalence and minimal cover

  • F covers G if every FD in G can be inferred from F. F and G are equivalent if each covers the other, that is F+ = G+.
  • A set of FDs is minimal (a minimal cover) if: (1) every FD has a single attribute on the right; (2) no FD can be removed without changing the closure; (3) no attribute can be removed from a left side without changing the closure.
  • Every set has at least one equivalent minimal set, and there can be several.
  • Canonical cover: a minimal cover in which FDs with the same left side are combined by union, so each left side is unique.

Added · methodMinimal cover in three steps.

  1. Split right sides. Replace X → YZ by X → Y and X → Z.
  2. Remove extraneous left-side attributes. For an FD with more than one left attribute, try dropping one attribute A. If the right side is still in the closure of the reduced left side (using all FDs), A is extraneous and is dropped.
  3. Remove redundant FDs. Try deleting each FD. If its right side is still in the closure of its left side under the remaining FDs, delete it for good.

Slide Example 4. F = {A→BC, B→C, A→B, AB→C}. Step 1: A→B, A→C, B→C, A→B, AB→C. Step 2: in AB→C, B alone gives C, so A is extraneous: it becomes B→C. Step 3: A→C is redundant (A→B→C). Result: {A→B, B→C}.

Slide Example 5. F = {B→A, D→A, AB→D}. Step 2: B+ already gives A, then AB→D fires, so A is extraneous in AB→D, which becomes B→D. Step 3: B→A is redundant (B→D→A). Result: {D→A, B→D}, and the only key is B.

Normal forms: 1NF, 2NF, 3NF, BCNF

DefineDifferentiateNumericalCheck

Definitions you need first

  • Prime attribute: a member of some candidate key. Non-prime: a member of no candidate key.
  • Full functional dependency: Y → Z where removing any attribute from Y breaks it. If some smaller part of Y still determines Z, it is a partial dependency. {SSN, PNUMBER} → HOURS is full. {SSN, PNUMBER} → ENAME is partial because SSN → ENAME.
  • Transitive dependency: X → Z derived from X → Y and Y → Z, where Y is not a key and Y does not determine X. SSN → DMGR_SSN is transitive through DNUMBER.
FormConditionFix when violated
1NFAll values atomic. No composite, multivalued or nested (relation-valued) attributes.Split into one value per cell: a multivalued attribute gets its own relation with the key, a nested relation is flattened by propagating the primary key.
2NF1NF and every non-prime attribute is fully dependent on every key.Move each partial dependency to its own relation, with its determinant as key.
3NFWhenever X → A holds, either (a) X is a superkey or (b) A is a prime attribute.Move each transitive dependency to its own relation.
BCNFWhenever X → A holds (non-trivial), X is a superkey. Condition (b) of 3NF is not allowed.Split on the violating FD (see decomposition).

The informal rhyme: 1NF, every attribute depends on the key. 2NF, on the whole key. 3NF, on nothing but the key. (BCNF adds: so help me Codd, even for prime attributes.)

Practical use

  • Designers usually normalise only up to 3NF, BCNF or 4NF. Higher forms rest on constraints that are hard to detect.
  • Denormalization stores the join of higher-normal-form relations as one base relation, trading redundancy for faster reads.

Decomposition: lossless join, dependency preservation, algorithms

DefineAlgorithmAddedCheck

Decomposition splits the universal relation R into D = {R1, …, Rn}, using the FDs. A good decomposition has three properties.

PropertyMeaningNeeded?
Attribute preservationEvery attribute of R appears in at least one Ri: R1 ∪ … ∪ Rn = R. Nothing is lost.Always
Dependency preservationThe union of the FDs projected onto each Ri is equivalent to F: (πR1(F) ∪ … ∪ πRn(F))+ = F+. Every FD can be checked inside a single relation, or derived from the ones that can.Desirable, can be sacrificed
Lossless (non-additive) joinFor every valid state r, the natural join of the projections gives back exactly r: *(πR1(r), …, πRn(r)) = r. "Loss" means loss of information (spurious tuples are added), not loss of tuples.Never sacrificed

CheckYour slide words dependency preservation as "all dependencies must either be a part of each of R1…Rn or be inferred from the union". It should be a part of at least one Ri (not each). Also the attribute-preservation formula shows "∑" from OCR, which should be the union sign ∪.

Lossless join test for two relations

Binary testD = {R1, R2} of R is lossless if and only if F+ contains (R1 ∩ R2) → (R1 − R2) or (R1 ∩ R2) → (R2 − R1). In words: the shared attributes must be a key of at least one of the two parts.

Added · methodTesting more than two relations (the tableau or chase test).

  1. Draw a table with one column per attribute of R and one row per relation Ri. In row i, write "a" in each column whose attribute is in Ri and a distinct "bi" elsewhere.
  2. For each FD X → Y, find rows that agree on all X columns. In the Y columns, make those rows equal: if one of them has "a", use "a", otherwise use one of the b symbols.
  3. Repeat until nothing changes. The decomposition is lossless if some row is all "a".

I used this test in code for Exercise 14 below.

Dependency preservation test

Added · methodFor each FD X → Y in F, set Z = X. Repeatedly, for every Ri, replace Z by Z ∪ ((Z ∩ Ri)+ ∩ Ri). When Z stops growing, the FD is preserved if Y ⊆ Z. If every FD passes, the decomposition preserves dependencies. This avoids computing the full projected FD sets.

Algorithm: 3NF by synthesis

Added · algorithmYour slides mention the algorithms in the recap but do not include them. This is the standard version.

  1. Find a minimal cover G of F.
  2. For each distinct left side X in G, create a relation holding X together with all attributes on the right sides of FDs that have left side X.
  3. If no relation contains a candidate key of R, add one relation made of a candidate key.
  4. Remove any relation that is wholly contained in another. Add any attribute not yet covered in a relation of its own.

The result is always in 3NF, lossless, and dependency-preserving. It can be larger than needed and may not be in BCNF.

Algorithm: BCNF by decomposition

Added · algorithm

  1. Start with the set {R}.
  2. Pick a relation Ri in the set and an FD X → Y that holds in it where X is not a superkey of Ri (Y not inside X).
  3. Replace Ri by two relations: X ∪ Y and Ri − Y. They share X, and X → Y makes the split lossless.
  4. Repeat until every relation is in BCNF.

The result is always lossless but may lose dependencies. The answer is not unique: it depends on which violating FD you pick first.

WorkedR(A, B, C, D), F = {AB→CD, D→A} (Exercise 10). Keys AB and BD. D → A has a non-superkey left side, so R is not in BCNF (it is in 3NF, since A is prime). Split on D → A: R1(D, A) and R2(B, D, C). Both are BCNF, and BD is the key of R2. The decomposition is lossless, but AB → CD is lost because A and B no longer sit in one relation.

Multivalued dependencies, 4NF, join dependencies, 5NF

DefineAdded

Multivalued dependencyX →→ Y holds in R if, whenever two tuples t1 and t2 have t1[X] = t2[X], there also exist tuples t3 and t4 with: t3[X] = t4[X] = t1[X]; t3[Y] = t1[Y] and t4[Y] = t2[Y]; t3[Z] = t2[Z] and t4[Z] = t1[Z], where Z = R − (X ∪ Y). Put simply: for each X value, the set of Y values is independent of the Z values.

  • An MVD is trivial if (a) Y ⊆ X, or (b) X ∪ Y = R. Otherwise it is non-trivial.
  • MVDs arise when a relation holds two independent multivalued facts about the same entity.

ExampleEMP(Ename, Pname, Dname): an employee works on several projects and has several dependents, independently. If Smith works on X and Y and has dependents John and Anna, the relation must hold all 2 × 2 = 4 combinations: (Smith, X, John), (Smith, X, Anna), (Smith, Y, John), (Smith, Y, Anna). Here Ename →→ Pname and Ename →→ Dname, and Ename is not a superkey (the key is all three attributes), so EMP is in BCNF but not in 4NF.

4NFR is in 4NF with respect to F (FDs and MVDs) if, for every non-trivial MVD X →→ Y in F+, X is a superkey of R.

Fix by splitting the independent facts: EMP_PROJECTS(Ename, Pname) and EMP_DEPENDENTS(Ename, Dname). This is the slide's EMP example.

Inference rules for FDs and MVDs

RuleStatement
IR1 to IR3Reflexive, augmentation, transitive rules for FDs (as before)
IR4 ComplementationX →→ Y implies X →→ (R − (X ∪ Y))
IR5 Augmentation (MVD)If X →→ Y and W ⊇ Z then WX →→ YZ
IR6 Transitive (MVD)X →→ Y and Y →→ Z imply X →→ (Z − Y)
IR7 ReplicationX → Y implies X →→ Y (every FD is an MVD)
IR8 CoalescenceIf X →→ Y, and some W with W ∩ Y empty, W → Z and Y ⊇ Z exist, then X → Z

Join dependency and 5NF

Join dependencyJD(R1, …, Rn) on R says every valid state r has a lossless decomposition into R1, …, Rn: *(πR1(r), …, πRn(r)) = r. An MVD is a JD with n = 2. A JD is trivial if one Ri equals R.

5NF (PJNF)R is in fifth normal form (project-join normal form) with respect to F if, for every non-trivial JD(R1, …, Rn) in F+, every Ri is a superkey of R.

ExampleSUPPLY(Sname, Part_name, Proj_name) with the rule: if supplier s supplies part p, project j uses part p, and s supplies something to j, then s supplies p to j. That gives JD(R1, R2, R3) with R1(Sname, Part_name), R2(Sname, Proj_name), R3(Part_name, Proj_name). No two-way split is lossless, but the three-way split is. Convert to 5NF by replacing SUPPLY with R1, R2 and R3.

SELECT: basic queries

Write SQLExplainCheck

SELECT blockSELECT <attribute list> FROM <table list> WHERE <condition>. It corresponds to relational algebra select, project and join, but SQL's SELECT is not algebra's σ.

  • SQL tables are multisets (bags): duplicate rows are allowed. A relation in the formal model is a set. Use PRIMARY KEY or UNIQUE, or DISTINCT in the query, to remove duplicates.
  • A column name used in two tables must be qualified: EMPLOYEE.Lname. Use aliases (tuple variables) when a table is used twice.
  • A missing WHERE means no condition. With two or more tables and no join condition you get the Cartesian product: large and wrong.
  • SELECT * returns all attributes.
  • Compare with NULL using IS NULL or IS NOT NULL, never = NULL. A join condition drops rows with NULL in the join attribute.

Clause order

SELECT <attributes or functions> (required)
FROM <tables> (required)
[WHERE <row condition>]
[GROUP BY <grouping attributes>]
[HAVING <group condition>]
[ORDER BY <attributes>]

Only SELECT and FROM are mandatory. A query is evaluated in this order: FROM, WHERE, GROUP BY, HAVING, then SELECT and ORDER BY. The FROM clause lists tables for the outer query only, not those used in nested queries.

A delete that breaks a constraint. Deleting an employee who still has a dependent is rejected by the foreign key (FOREIGN KEY constraint failed) because the default rule is RESTRICT. Delete the dependent first, or declare ON DELETE CASCADE.

  • INSERT without a column list needs values in the order of the CREATE TABLE. With a column list, any column you leave out gets NULL (or its default). One-page cheat sheet

FD rules

  • Reflexive: Y ⊆ X gives X→Y
  • Augmentation: X→Y gives XZ→YZ
  • Transitive: X→Y, Y→Z give X→Z
  • Union, decomposition, pseudotransitivity
  • X→Y implied iff Y ⊆ X⁺

Closure X⁺

  • Start with X
  • Add RHS of any FD whose LHS is inside
  • Repeat until nothing is added

Candidate keys

  • Never on a RHS: in every key
  • Only on RHS: in no key
  • Add attributes until closure = R, keep minimal sets

Minimal cover

  • 1 Split RHS to single attributes
  • 2 Drop extraneous LHS attributes
  • 3 Drop redundant FDs
  • Canonical: merge same LHS

Normal forms

  • 1NF atomic values
  • 2NF no partial dependency
  • 3NF X superkey or A prime
  • BCNF X superkey
  • 4NF MVD needs superkey
  • 5NF JD needs superkeys

Decomposition

  • Attribute preservation: always
  • Lossless: never give up. Binary test: R1∩R2 → R1−R2 or R2−R1
  • Dependency preservation: can give up
  • 3NF synthesis: always both. BCNF: lossless only

SQL clause order

  • SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY
  • Only SELECT and FROM required
  • WHERE rows, HAVING groups

Nested queries

  • IN, ANY, ALL, EXISTS, NOT EXISTS
  • Correlated: inner uses outer column
  • "For all" = double NOT EXISTS
  • NULL: IS NULL, not = NULL

Joins and updates

  • JOIN ON, NATURAL, LEFT/RIGHT/FULL OUTER, CROSS
  • INSERT, UPDATE, DELETE affect one table
  • DELETE with no WHERE empties the table
  • View = stored query
