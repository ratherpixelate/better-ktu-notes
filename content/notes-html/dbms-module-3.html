Transactions and why they fail

DefineNumericalLikely exam

TransactionA logical unit of database processing with one or more access operations (read, insert, update, delete). It is an atomic unit: done in full or not at all. Boundaries are begin and end transaction.

  • Single-user system: one user at a time. Multiuser: many users at once.
  • Interleaved processing: concurrent execution on one CPU. Parallel processing: several CPUs.
  • A database is a set of named data items (field, record or block; granularity does not change the theory).
read_item(X): find block of X, copy to buffer if absent, copy X to program variable.
write_item(X): find block, copy to buffer, copy program variable X into buffer, store block to disk now or later.

Temporary update (dirty read)T1 updates X, T2 reads it, then T1 aborts and X is restored. T2 used a value that never existed.T1: w(X)=100, T2: r(X)=100, T1 aborts, X goes back to 80.

Why recovery is needed: causes of failure

  • System crash: hardware or software error, main memory contents lost.
  • Transaction or system error: overflow, divide by zero, wrong input, logical error, user interrupt.
  • Local error or exception found by the transaction: data not found, insufficient balance, programmed abort.
  • Concurrency control aborts it (serializability violation or deadlock).
  • Disk failure: head crash, read/write malfunction.
  • Physical problems and catastrophes: power or AC failure, fire, theft, sabotage, wrong tape mounted.

Operations the recovery manager tracks

  • begin_transaction, read or write, end_transaction (then check: commit or abort?).
  • commit_transaction: success. Changes will not be undone.
  • rollback (abort): failure. All changes must be undone.
  • undo: like rollback but for a single operation. redo: reapply operations of a committed transaction.

The system log

LogA sequential file (journal) on disk that records every operation affecting database items. It survives everything except disk failure or a catastrophe, so it is also backed up to archival storage.

Log recordMeaning
[start_transaction, T]T started
[write_item, T, X, old_value, new_value]T changed X (old = BFIM, new = AFIM)
[read_item, T, X]T read X. Needed only if cascading rollback is possible.
[commit, T]T finished successfully
[abort, T]T aborted
  • Protocols that avoid cascading rollbacks do not need read entries. Strict protocols need no new_value in write entries.
  • Commit point: all database operations of T are done and their effect is recorded in the log. Then [commit, T] is written.
  • Force-writing the log: before commit, any unwritten part of the log is flushed to disk. After a crash only log entries on disk count.
  • T with [start] but no [commit] is rolled back. T with [commit] is redone if needed.

Schedules and recoverability

DefineDifferentiateNumerical

Schedule (history)An ordering of the operations of n transactions such that the operations of each Ti appear in the same order as in Ti. Operations of different transactions may interleave.

  • Recoverable: no transaction T commits until every transaction that wrote an item T read has committed.
  • Cascadeless (avoids cascading rollback): every transaction reads only items written by committed transactions.
  • Strict: a transaction can neither read nor write X until the last transaction that wrote X has committed (or aborted).
  • Cascaded rollback: an uncommitted transaction that read from a failed one must also roll back.

Worked classification (all run in code)

w1(X) r2(X) c2 c1NoNoNoT2 commits before T1, which it read from.
w1(X) w2(X) c1 c2YesYesNoT2 overwrote uncommitted X (no read, so cascadeless, but not strict).
w1(X) c1 r2(X) w2(X) c2YesYesYesEverything touches X only after the last writer committed.

Serializability

DefineDifferentiateNumericalDrawLikely exam
  • Serial: every transaction runs consecutively, no interleaving. Serializable: equivalent to some serial schedule. Serializable is not the same as serial. It is correct and still efficient.
  • Result equivalent: same final database state (can be by luck, so not used).
  • Conflict: two operations conflict if they are from different transactions, on the same item, and at least one is a write.
  • Conflict equivalent: conflicting operations are in the same order in both schedules. Conflict serializable: conflict equivalent to some serial schedule.
  • Only the committed projection of a schedule is checked in practice.
OperationsConflict?
r1(X), r2(X)No (two reads)
r1(X), w2(X)Yes
w1(X), r2(X)Yes
w1(X), w2(X)Yes
any pair on different itemsNo

Algorithm 17.1: precedence graph test

  1. Make a node for every transaction.
  2. For each r_j(X) after w_i(X), draw Ti → Tj.
  3. For each w_j(X) after r_i(X), draw Ti → Tj.
  4. For each w_j(X) after w_i(X), draw Ti → Tj.
  5. Cycle = not conflict serializable. No cycle = serializable. A topological order of the graph is an equivalent serial schedule.

NumericalTest Sh: r1(X) w1(X) r2(Y) w2(Y) r1(Y) w1(Y) r2(X) w2(X). Edges: w1(X) before r2(X) gives T1→T2. r2(Y) before w1(Y) gives T2→T1. Cycle, so not conflict serializable.

View serializability

View equivalentS and S' are view equivalent if (1) same transactions and operations, (2) every read reads the value written by the same write (or the initial value) in both, and (3) the last write of each item is by the same transaction in both.

  • Conflict serializable ⇒ view serializable. The reverse is false.
  • They agree under the constrained write assumption (new X = f(old X)). With blind writes (write without read) a schedule can be view serializable only.

Slide exampleSa: r1(X); w2(X); w1(X); w3(X); c1; c2; c3. w2(X) and w3(X) are blind writes. Conflict edges T1→T2 and T2→T1 form a cycle, so not conflict serializable. T1 reads the initial X, and T3 writes X last, exactly as in the serial order T1, T2, T3, so it is view serializable (checked by trying all 6 orders).

Semantic equivalenceWith commutative operations (debit, credit) a non-conflict-serializable schedule can still be correct. Slide example Sh with X=100, Y=200, T1 debits X by 10 and credits Y by 10, T2 debits Y by 20 and credits X by 20: final X=110, Y=190, same as a serial run. I used these start values; the slide gives none.

Two-phase locking

DefineDifferentiateNumericalLikely exam

PurposeConcurrency control enforces isolation through mutual exclusion among conflicting transactions, keeps the database consistent, and resolves read-write and write-write conflicts. It decides whether T1 or T2 gets item A and whether the other waits or rolls back.

  • Lock: permission to read or write item X for a transaction. lock(X) and unlock(X) are atomic operations.
  • Shared (read) lock: many transactions can hold it, nobody can write. Exclusive (write) lock: only one holder, no other lock allowed.
  • Lock manager keeps a lock table (transaction id, item, mode, pointer), often a linked list.
  • Well-formed transaction: locks an item before reading or writing it, never locks an already locked item it holds, never unlocks a free item.

Lock and unlock code (slides)

lock(X):   B: if LOCK(X) = 0  then LOCK(X) <- 1
               else wait until LOCK(X)=0 and the lock manager wakes T; goto B
unlock(X): LOCK(X) <- 0; if any transaction is waiting, wake one of them
  • Lock upgrade: read lock to write lock, allowed if no other transaction holds a read lock on X, else wait.
  • Lock downgrade: write lock to read lock.

The two-phase rule

2PLA transaction has a growing (locking) phase where it only acquires locks, then a shrinking (unlocking) phase where it only releases locks. Once it unlocks anything it can never lock again. Guarantees conflict serializability.

VariantRuleDeadlock?
BasicLocks incrementally, any time before first unlock.Possible
Conservative (static)Locks all items before it starts. If it cannot, it waits and holds nothing.Free of deadlock
StrictHolds locks until it commits or aborts. Most commonly used.Possible
Rigorous (Added)Holds all locks (read and write) until commit or abort.Possible

Strict 2PL gives strict schedules (so no cascading rollback). Slide 18-16 also says "two algorithms" and then lists three.

Numerical: the slide example (X=20, Y=30)

T1: read Y; X := X + Y; write X.   T2: read X; Y := X + Y; write Y.
Serial T1 then T2: X = 20+30 = 50, Y = 50+30 = 80
Serial T2 then T1: Y = 20+30 = 50, X = 20+50 = 70, so X=70, Y=50
Interleaved with early unlocks (T1 unlocks Y before locking X): T1 read Y=30, T2 read X=20 and wrote Y=50, then T1 writes X = 20+30 = 50: X=50, Y=50

Why it failsX=50, Y=50 matches neither serial result. It is not serializable because T1 and T2 unlock and then lock again, which violates two-phase locking. Moving the unlocks after the last lock (T1' and T2') makes it serializable but allows deadlock.

Deadlock and starvation

DefineDifferentiateDrawLikely exam

DeadlockA set of transactions where each waits for a lock held by another in the set, so none can proceed.

Slide exampleT1' holds read_lock(Y) and asks write_lock(X). T2' holds read_lock(X) and asks write_lock(Y). Both follow 2PL, both wait forever.

Three ways to deal with it

ApproachHowCost
PreventionConservative 2PL: lock everything first, so nobody waits while holding locks.Low concurrency, must know items in advance.
Detection and resolutionAllow deadlock. Keep a wait-for graph: node per transaction, edge Ti → Tj when Ti waits for Tj. A cycle means deadlock. Pick a victim in the cycle and roll it back.Graph upkeep, wasted work.
Avoidance (timestamp schemes)Roll a transaction back as soon as waiting might make a cycle. Wait-die and wound-wait use timestamps.Some needless aborts.

Wait-die and wound-wait

Timestamp TS(T) = start time. Smaller TS means older. Ti requests an item locked by Tj.

Ti is older (TS(Ti) < TS(Tj))Ti is younger (TS(Ti) > TS(Tj))
Wait-dieTi waitsTi dies (aborts, restarts with same TS)
Wound-waitTi wounds Tj (Tj aborts)Ti waits
  • Wait-die: older waits for younger, never the other way. Wound-wait: younger waits for older. No cycle is possible in either.
  • A restarted transaction keeps its original timestamp, so it eventually becomes the oldest and cannot starve forever.

AddedSlides name the two schemes but give no rules. The rules above are from the textbook. Also not in the slides: no waiting (abort instead of waiting, restart after a delay) and cautious waiting (wait only if the holder itself is not blocked).

Choosing the victim

CheckSlides 19-4 and 19-5 are from an Operating Systems book (Silberschatz) and are filed under database recovery by mistake. They fit here: abort all deadlocked processes or one at a time until the cycle goes. Choose by priority, time computed and remaining, resources used and needed, how many must be aborted, interactive or batch. Rollback to a safe state, and include the number of rollbacks in the cost so one transaction is not always picked.

Starvation

  • A transaction waits or restarts again and again and never proceeds.
  • Causes: the same victim chosen each time; priority-based scheduling; in wound-wait a long-running older transaction keeps wounding younger ones.
  • Fixes: first-come-first-served lock queue, count rollbacks in the victim cost, keep the original timestamp.

Timestamp ordering

DefineNumericalLikely exam

TimestampA monotonically increasing number showing the age of a transaction. Larger = younger. Each item X keeps read_TS(X) (largest TS of a successful read) and write_TS(X) (largest TS of a successful write). The DBMS runs conflicting operations in timestamp order, so the schedule is equivalent to the serial order of timestamps.

Basic timestamp ordering

write_item(X)read_TS(X) > TS(T) or write_TS(X) > TS(T)Abort and roll back T, reject the operation (a younger transaction already read or wrote X).

  • Basic TO is deadlock free (nobody waits) but can cause cyclic restart (starvation) and cascading rollback, and is not recoverable by itself.

Strict timestamp ordering

T issuesConditionAction
write_item(X)TS(T) > read_TS(X)Delay T until the transaction T' that wrote or read X has committed or aborted.
read_item(X)TS(T) > write_TS(X)Delay T until the transaction T' that wrote X has committed or aborted.
  • Gives strict schedules (so recoverable and cascadeless). A transaction only ever waits for an older one, so there is no cycle and it is deadlock free.

AddedThomas write rule (not in slides). In basic TO, if write_TS(X) > TS(T) but read_TS(X) ≤ TS(T), T's write is obsolete. Instead of aborting, ignore the write. Run in code: T2 (TS 10) writes X, then T1 (TS 5) writes X. Basic TO aborts T1. With Thomas rule T1's write is skipped. Gives view (not always conflict) serializable schedules.

Log, BFIM and AFIM

For recovery the log needs the value before modification (BFIM, before image) and after modification (AFIM, after image). Each log record also has Back P and Next P pointers to the previous and next record of the same transaction.

Data update and caching

TermMeaning
Immediate updateUpdates reach the database disk before the transaction commits.
Deferred updateWrites happen only after the transaction ends (or after a set of transactions finish).
In-place updateDisk copy is overwritten by the cache version.
Shadow updateThe new version goes to a separate disk location, old copy is kept.
  • The cache manager brings items into the database cache, and they are flushed to disk later. Flushing is controlled by two bits: pin-unpin (pinned means do not flush) and modified (dirty, holds the AFIM).
  • Undo: restore all BFIMs to disk (remove AFIMs). Redo: restore all AFIMs. Recovery can use only undos, only redos, or both.

Write-ahead logging (WAL)

  • For undo: before an AFIM overwrites the BFIM on disk, the BFIM must be written to the log and the log forced to stable storage.
  • For redo: before a transaction commits, all its AFIMs must be in the log on stable storage.

Checkpointing

  1. Suspend transaction execution briefly.
  2. Force-write all modified buffers to disk.
  3. Write a [checkpoint] record to the log and save the log.
  4. Resume.

Recovery only needs to redo or undo transactions that appear after the last checkpoint (plus those active at it).

Steal, no-steal, force, no-force

Policy pairRecovery needed
Steal / No-forceUndo / Redo (most flexible)
Steal / ForceUndo / No-redo
No-steal / No-forceNo-undo / Redo

Steal: cache can be flushed before commit. No-steal: not until commit. Force: flushed immediately at commit. No-force: flushing deferred after commit.

Recovery schemes

Deferred updateUpdates only in the log until commit. At commit, written to disk under WAL. Crash: redo committed transactions from the log. Active ones are ignored (no AFIM reached disk).NoYes

Shadow paging

  • No log needed. Two directories: current and shadow, both with one entry per page.
  • On the first write to a page the DBMS copies it to a new free block and updates only the current directory. The old page stays untouched.
  • Commit: the current directory becomes the new shadow directory. Failure: discard the current directory and use the shadow one. No undo or redo.
  • Drawbacks (Added, from the textbook): pages scatter on disk, garbage collection of old pages, hard with concurrent transactions.

Numerical: what to redo and undo

AnswerT1: committed before the checkpoint, its changes were flushed, no action. T2 and T4: committed after the checkpoint, redo. T3 and T5: no commit record, undo (use BFIMs, backwards through the log). Redo goes forward through the log, undo goes backward.

Backup strategies

DefineDifferentiateAdded

AddedYour slides stop at recovery from crashes and do not cover backup at all. This section is from the textbook and standard practice. The log is already backed up to archival storage (slide 17-22), which is the link to this topic.

BackupA copy of the database (and log) kept separately so the database can be restored after media failure or a catastrophe, which log-based recovery on the same disk cannot handle.

TypeWhat it copiesRestore needs
FullWhole databaseJust the full backup
IncrementalChanges since the last backup of any kindFull + every incremental in order
DifferentialChanges since the last full backupFull + latest differential

ExampleIllustrative: full backup 100 GB, then 5 GB of new changes each day for 3 days. Differential on day 3 holds 15 GB, restore = full + 1 set = 115 GB in 2 sets. Incremental holds 5 GB per day, restore = full + 3 sets = 115 GB in 4 sets. Same data, incremental backs up faster but restores slower.

Other termsMeaning
Hot (online) vs cold (offline)Hot: taken while the database runs, needs the log to be consistent. Cold: database shut down, simple and consistent.
Logical vs physicalLogical: SQL dump of data (mysqldump). Physical: copy of data files.
Point-in-time recoveryRestore a full backup, then replay the log up to a chosen moment.
Archive log / remote copyLog backed up to tape or another site against disaster.
