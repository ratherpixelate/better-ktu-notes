Types of database testing

TypeWhat it checks
Functional (black-box)Data validation, constraint enforcement, query results, business logic in the DB, without seeing the implementation.
Structural (white-box)Table design, relationships, index use, triggers and stored procedures, execution paths inside them.

Schema and constraint testing

NumericalDefineLikely exam

MethodCreate test tables, insert valid and invalid records, modify keys, try deleting parent records. Valid data must succeed, invalid data must produce an error, and modify or delete must respect PK and FK rules.

ConstraintWhat it doesValidate by
PRIMARY KEYUniquely identifies a row, no NULL, no duplicateinsert a duplicate or NULL
FOREIGN KEYReferential integrity between tablesinsert a child with no parent
UNIQUENo two rows share the valueinsert a duplicate value
NOT NULLThe attribute must have a valueinsert NULL
CHECKRestricts values by an expression, e.g. CHECK (age > 0)insert age = -1
DEFAULTGives a value if none is suppliedinsert without the column, default must appear

CheckFour problems in the usual version of these test cases: (1) the comment on test 2 says "Violates PK" but it violates the foreign key. (2) Test 3 uses the table name "Employee Contact" with a space, which is not valid SQL, I used EmployeeContact. (3) Tests 6 and 7 cannot both run on the same foreign key: 6 needs RESTRICT, 7 needs CASCADE. Run 7 on a different table or after altering the rule. (4) Test 5 uses EmpID 106 before 105. Harmless, but keep IDs in order in your own record.

AddedDialect: SQLite needs PRAGMA foreign_keys=ON or the FK tests wrongly pass. MySQL InnoDB enforces foreign keys always. Older MySQL (before 8.0.16) accepted CHECK but ignored it, so the CHECK tests would wrongly pass there. MySQL error text differs, e.g. error 1062 Duplicate entry, 1452 Cannot add or update a child row. As far as I know those are the right codes.

Transaction, concurrency, error and security testing

DefineDifferentiateAdded
PropertyHow to testExpected
AtomicityInsert several rows in one transaction and cause an error midwayAll rolled back, no partial change
ConsistencyCheck constraints after the transactionNo invalid state
IsolationRun concurrent transactions. Cases: dirty read, non-repeatable read, phantom read (depending on isolation level)No interference
DurabilityCommit, restart the DBData is still there

Run in code (atomicity)Transaction: insert employee 120 (valid), then insert employee 121 with DeptID 99. The second fails with FOREIGN KEY constraint failed. After ROLLBACK, employee 120 is not in the table (count 0). No partial change.

Levels of isolation (textbook)

LevelGuarantee
0Does not overwrite dirty reads of other transactions
1No lost updates
2No lost updates and no dirty reads
3No lost updates, no dirty reads, repeatable reads. True isolation

CheckThese 0 to 3 levels are the textbook (Elmasri) levels. The SQL standard levels are READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ and SERIALIZABLE, which are the ones MySQL uses, as in Module 3. Do not mix them in one answer. Slide wording for level 0 is also muddled: it means the transaction does not overwrite uncommitted data of others.

  • Concurrency testing: lost updates, dirty writes, deadlocks. Open two sessions and interleave statements by hand.
  • Error and exception testing: incorrect queries, invalid constraints, invalid data types, violated foreign keys, overflow. Each must give a clean error, not a crash.
  • Security testing: access control, role permissions, SQL injection tests (see Safe code).

AddedWhy isolation testing needs two sessions: one connection alone can never see a dirty read. Use two mysql client windows, SET TRANSACTION ISOLATION LEVEL ... then START TRANSACTION in each.

A simple application: student register

import mysql.connector

def get_conn():
    return mysql.connector.connect(host="localhost", user="root",
                                   password="root", database="college")

def add_student(rollno, name, branch):
    db = get_conn(); cur = db.cursor()
    cur.execute("INSERT INTO student VALUES (%s,%s,%s)", (rollno, name, branch))
    db.commit(); db.close()

def find_by_branch(branch):
    db = get_conn(); cur = db.cursor()
    cur.execute("SELECT * FROM student WHERE branch=%s", (branch,))
    rows = cur.fetchall(); db.close(); return rows

def update_branch(rollno, branch):
    db = get_conn(); cur = db.cursor()
    cur.execute("UPDATE student SET branch=%s WHERE rollno=%s", (branch, rollno))
    db.commit(); db.close()

def delete_student(rollno):
    db = get_conn(); cur = db.cursor()
    cur.execute("DELETE FROM student WHERE rollno=%s", (rollno,))
    db.commit(); db.close()

Safe code: SQL injection, commit, errors

DefineDifferentiateNumericalLikely exam

SQL injectionAn attacker puts SQL into an input so that it changes the meaning of your query. It can read, change or destroy data. Prevent it with parameterized queries: put %s in the SQL and pass the values separately as a tuple.

Run in codeTable of 4 students. User types x' OR '1'='1 as the name.
Unsafe: "SELECT * FROM student WHERE name='" + user + "'" becomes WHERE name='x' OR '1'='1' and returns all 4 rows.
Safe: execute("... WHERE name=%s", (user,)) treats the whole text as one name and returns 0 rows.

Other points

  • commit(): INSERT, UPDATE and DELETE are not saved without it. Run in code: insert, close the connection without commit, reopen: 0 rows. SELECT needs no commit.
  • rollback() undoes everything since the last commit. This is transaction control from Module 3 in Python: several statements, one commit() at the end, rollback() on error.
  • Wrap database code in try / except mysql.connector.Error and finally: close(), so a failed query does not leave the connection open.
  • Do not hard-code the password. Read it from an environment variable or a config file. Use a user with only the privileges the app needs.
  • Always use a WHERE on UPDATE and DELETE. Without it every row changes.
  • Close the cursor and the connection when done.
try:
    cur.execute("UPDATE acc SET bal=bal-%s WHERE id=%s", (100, 1))
    cur.execute("UPDATE acc SET bal=bal+%s WHERE id=%s", (100, 2))
    db.commit()               # both or neither
except mysql.connector.Error as e:
    db.rollback()
    print("failed:", e)
finally:
    cur.close(); db.close()

AddedTransactions in the connector: by default autocommit is off, so changes wait for commit(). As far as I know that is the default for MySQL Connector/Python. The try/except example is the standard pattern but was not run against MySQL.

One-page cheat sheet

Revise the night before

Testing types

  • Functional (black-box), structural (white-box)
  • Regression, performance, interface

Validate a constraint

  • PK: duplicate or NULL
  • FK: child with no parent
  • UNIQUE: duplicate
  • NOT NULL: NULL
  • CHECK: age = -1
  • DEFAULT: omit the column

Method

  • Valid data succeeds, invalid errors
  • Modify and delete must respect PK, FK

Transaction testing

  • A: error midway, all rolled back
  • C: no invalid state
  • I: concurrent sessions
  • D: commit, restart, data persists

Python steps

  • import, connect, cursor, execute, commit or fetch, close
  • pip install mysql-connector-python

Connector calls

  • fetchall list of tuples, fetchone first row
  • rowcount, lastrowid
  • executemany list of tuples

Safety

  • %s placeholders, values as tuple
  • commit() or nothing saved
  • rollback() on error
  • No password in code
  • Never UPDATE/DELETE without WHERE
